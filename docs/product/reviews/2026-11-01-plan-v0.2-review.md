# Auvora: Review of plan v0.2

Reviewed: `docs/product/archive/plan-v0.2.md` (v0.2, 1 Nov 2026)
Purpose: list gaps and drawbacks, then ask every question that has to be answered before plan v1.0 can be frozen.

**How to answer:** fill in `Answer:` under each question. Write `R` to accept my recommendation. Write `?` if you want me to explain the trade-off first. When the answers are in, I'll produce plan v1.0 with ADRs, the MVP, phased sequencing with measurable exit criteria, repo layout and the first sprint backlog.

---

## 0. Verdict

The security thinking is strong: secure defaults, no Implicit or ROPC grants, actor/subject semantics, fail-closed replay protection, no bespoke XML-DSig. As a **principles document** it is good.

As a **build plan** it is not ready yet:

1. It describes the whole category, not a product.
2. It defers the important decisions to "ADRs later" (§27 lists 16 of them).
3. Several core subsystems are missing entirely.
4. The roadmap order has dependency inversions.
5. Nothing is quantified: no team, no timeline, no scale targets, no SLOs, no MVP.

## 2. Gaps: what is missing

### 2.1 Missing product capabilities

- **Authentication flow engine.** How are login, registration, recovery and step-up composed? Options are fixed flows, a policy-driven state machine, or a visual journey builder. Headless and hosted UI both need one **flow API** (see Q33).
- **Extensibility** (D5): sync hooks (pre-registration, pre-token claims enrichment, post-login), async webhooks (signed, retried, at-least-once, replayable), and possibly a sandboxed Wasm runtime.
- **Communications** (D8): email and SMS providers, template engine, i18n, per-tenant sender domains (SPF/DKIM), and suppression and bounce handling.
- **Bot and abuse protection:** CAPTCHA/Turnstile integration, SMS-pumping/toll-fraud controls, signup abuse, disposable-email detection.
- **End-user self-service account portal:** profile, password, passkeys, MFA devices, sessions, linked accounts, consent grants, data export, account deletion.
- **B2B organization features:** invitations, verified domains, per-org SSO and MFA policy, per-org branding, and a **self-service SSO/SCIM setup portal for the customer's IT admin**, which is the WorkOS-style wedge.
- **User migration:** bulk import, **lazy (trickle) migration** via hook, and password-hash import (bcrypt, scrypt, Firebase-scrypt, PBKDF2, Argon2, MD5/SHA legacy with forced rehash). The plan mentions "migration guides" only.
- **Privacy and consent:** GDPR/DPDP data-subject export and erasure, terms/privacy-version acceptance tracking, marketing consent, age gating and parental consent, PII classification, data residency.
- **Admin console** has a feature list (§22) but **appears in no roadmap phase**.
- **Platform self-administration:** bootstrap of the first admin, how Auvora authenticates its own admins (dogfooding), break-glass for the platform itself, and the control-plane admin permission model.
- **Configuration as code:** export/import, environment promotion (dev→staging→prod), GitOps, drift detection, and a Terraform provider (currently Phase 10, which is too late for enterprises).
- **Analytics and reporting:** login funnel, MAU/DAU, auth method mix, failure reasons, risk events.
- **Managed SaaS concerns** (if a cloud exists): signup, plans, metering (MAU/M2M tokens), billing, quotas, noisy-neighbor isolation, per-tenant rate limits.
- **Mobile specifics:** app attestation (App Attest / Play Integrity), native first-party login (OAuth for First-Party Apps draft), OIDC Native SSO, deep-link/universal-link redirect handling.
- **Push MFA implies building an authenticator app.** That is hidden scope: an iOS and Android app, push infrastructure (APNs/FCM) and number matching.
- **API lifecycle:** versioning scheme, deprecation policy, pagination/filter conventions, error format (RFC 9457 Problem Details), idempotency keys, ETag/optimistic concurrency.
- **Upgrade story:** zero-downtime rolling upgrades, expand/contract migrations, N-1 compatibility, signing-key and session survival across upgrades.
- **Search** across users, audit and events at scale. Is Postgres full-text search enough, or do you need an external index?

### 2.3 Missing non-functional and cross-cutting decisions

- Crypto provider: aws-lc-rs (FIPS 140-3 path) vs ring vs RustCrypto. This affects rustls, JOSE and WebAuthn crates.
- Post-quantum: hybrid TLS (X25519MLKEM768 in rustls), ML-DSA for JOSE/X.509, crypto-agility plan (§17 mentions agility only generically).
- ID format and external ID shape.
- Time handling, clock-skew budget, NTP requirement.
- Rate-limiting design: algorithm, keys (IP, account, tenant, client), storage, fail mode.
- Argon2id CPU-exhaustion DoS: a concurrency cap and queueing on the hashing path.
- Logging PII policy and redaction.
- Accessibility target (WCAG 2.2 AA) and RTL language support for hosted UI.
- Supported platforms: Postgres versions, OS/arch (amd64/arm64), Kubernetes versions, browsers.
- Release cadence, semver, LTS, security-patch SLA.
- Documentation site and docs-as-code.
- Self-hosted telemetry (opt-in or none).

### 2.4 Missing abuse cases (add to §20.2)

- **SSRF** via tenant-supplied URLs: OIDC discovery, JWKS URIs, SAML metadata URLs, webhook endpoints, `logo_uri`, `jwks_uri` in DCR, `request_uri`.
- **Pre-account-takeover:** an attacker registers the victim's email before the victim signs in via social/SSO.
- Email-change account takeover; unverified email trusted from IdP (the "nOAuth" class).
- MFA fatigue/push bombing, SIM-swap, OTP relay/phishing proxies (AiTM, Evilginx class).
- Open redirect, wildcard redirect URIs, localhost/loopback redirect rules for native apps.
- OAuth consent phishing (malicious third-party apps).
- Clickjacking, CORS misconfiguration, XS-leaks on login pages, CSRF on flows.
- Unicode/homoglyph usernames, email normalization collisions, case-folding.
- Timing attacks on user lookup and token comparison.
- SMS pumping/toll fraud; email bombing via reset/OTP endpoints.
- ReDoS in tenant-supplied regex (attribute mapping, policy).
- Tenant-admin privilege escalation into other tenants or into the platform.
- Insider/operator abuse (Auvora Cloud staff).
- Supply-chain attacks (crates, npm packages, CI).
- Backup exfiltration and key-material exposure in backups.
- Downgrade of authentication method (passkey → SMS fallback).

## 3. Roadmap problems (sequencing and dependencies)

1. **Social login, magic links, email OTP and SMS OTP** are in §6 but in **no phase**.
2. **Admin console** is in no phase.
3. **Webhooks, events and extensibility** are in no phase.
4. **Key management is Phase 9, but Phase 2 signs tokens.** The key abstraction (local + KMS interface + rotation) must be Phase 1–2.
5. **Authorization is Phase 7, but the control plane needs admin permissions in Phase 1**, and B2B org roles are needed long before Phase 7.
6. **Delegated (tenant) administration is Phase 9**, but multi-tenancy in Phase 1 needs tenant-scoped admins immediately.
7. **Password login is Phase 1 but hosted UI is Phase 3.** Phases 1–2 need some UI.
8. **Rate limiting, bot protection and notifications** must exist before anything is internet-facing (Phase 1), not as "risk signals" in Phase 4.
9. **Device flow, token exchange, PAR, JAR and DPoP** are in §7 but not placed. Token exchange first appears in Phase 6, yet support access (Phase 8) and agents depend on it.
10. **Mobile SDKs (Phase 3) come before passkeys (Phase 4).** Mobile SDKs need passkeys and app attestation.
11. **Multi-region is Phase 9**, but its prerequisites must be decided in Phase 0: ID scheme, tenant home-region pinning, and cell routing.
12. **OIDF conformance certification is Phase 10.** The conformance suite should run in CI from Phase 2.
13. **Upgrade/migration tests** must start in Phase 1, not appear only as a test layer.
14. **No managed-cloud phase** (signup, billing, metering), if a cloud is intended.
15. **Phases are strictly sequential, with no parallel tracks**, no durations, no release labels (alpha/beta/GA), and no dogfood application.
16. **The differentiators come last.** Supervised Support Access is Phase 8 and agent identity is effectively unplanned. If they are the wedge, they come too late.

- **Agent:** an autonomous principal that acts *on behalf of* a user or service, with an owner and delegation records.
- **OAuth client:** a protocol artifact, not a principal.
Drop "service principal" and "robot account." Accept?
