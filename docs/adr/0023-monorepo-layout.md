# ADR-0023: Monorepo layout

- **Status:** Accepted
- **Date:** 2026-11-01
- **Deciders:** Kamaal Khan (owner)
- **Plan refs:** plan.md §4 D23, §5.5
- **Related:** ADR-0004, ADR-0005, ADR-0022, ADR-0024, ADR-0046, ADR-0047, ADR-0111, ADR-0112

## Context

The server, frontends, JS SDKs, deployment artifacts, conformance harnesses and docs evolve together. API changes must update SDKs, console, docs and Terraform in one PR (principle 15). The open-core model requires a clean separation between AGPL code and `ee/` commercial code (ADR-0004).

## Decision

1. A single repository `auvora` contains:
   ```
   crates/          Rust workspace members (AGPL-3.0), one crate per plan §5.5
   ee/crates/       Commercial crates (Auvora Commercial License)
   apps/            console, hosted-ui, org-portal
   packages/        JS/TS packages: js, react, nextjs, node, elements, vue, angular, svelte,
                    api-client, mcp, tokens, ui (internal)
   sdks/            non-JS SDKs, one dir per language: go, python, java, dotnet, swift,
                    kotlin, react-native, flutter, php, ruby, rust-client
   mobile/          Auvora Authenticator app (ios/, android/)
   integrations/    terraform-provider, mcp-server, framework plugins not published via packages/
   deploy/          helm/, compose/, terraform-modules/
   conformance/     OIDF, SAML, SCIM, WebAuthn harnesses
   fuzz/            cargo-fuzz targets
   bench/           k6 + criterion benchmark suites
   docs/            Starlight site, adr/, threat-models/, specs/
   examples/        reference/dogfood apps
   scripts/         repo tooling (check-adrs, release, codegen)
   ```
2. **Workspaces:** a root `Cargo.toml` workspace including `crates/*` and `ee/crates/*`. A root `pnpm-workspace.yaml` includes `apps/*`, `packages/*` and `examples/*`.
3. **EE separation:**
   - AGPL crates MUST NOT depend on `ee/` crates.
   - EE features are wired in via traits defined in open crates and registered behind the Cargo feature `ee`.
   - Release builds are produced in two flavours: `auvora` (open) and `auvora-ee`.
   - `cargo-deny` and a custom check enforce the dependency direction.
4. **License files:** root `LICENSE` (AGPL-3.0) and `ee/LICENSE` (commercial). Each `packages/*`, `deploy/helm` and the Terraform provider carries `LICENSE` (Apache-2.0). Every source file has an SPDX header.
5. **Everything lives in this one repository (owner directive).** Other-language SDKs live in `sdks/<lang>/`, the Authenticator app in `mobile/`, and the Terraform provider and other integrations in `integrations/`. Where an ecosystem requires a dedicated repository for publishing (e.g. Go module paths, Swift Package Manager, Terraform Registry), a **read-only mirror** is generated by CI from the subdirectory (git subtree split); the monorepo remains the only place where changes are made. Detailed placement rules are in ADR-0111.
6. **Generated code** (OpenAPI spec, TS API client) is committed. CI fails if regeneration produces a diff.
7. **Tooling:** `just` as the task runner (`just dev`, `just test`, `just conformance`). Toolchains are pinned via `rust-toolchain.toml` and `.nvmrc`/`packageManager`.
8. **Ownership:** `CODEOWNERS` gives crypto/protocol crates (`auvora-crypto`, `auvora-jose`, `auvora-oauth`, `auvora-saml`, `auvora-authz`, `auvora-sessions`) mandatory security-owner review.

## Rationale

Atomic cross-cutting changes, a single CI, and one place for every artifact: an API change updates the server, every SDK, docs and Terraform in one commit. Ecosystem publishing constraints are met with CI-generated read-only mirrors instead of separate sources of truth.

## Alternatives considered

- **Polyrepo for everything**: version skew and multi-PR changes. Rejected.
- **Separate repos per language SDK**: version skew, multi-PR changes and SDK drift. Rejected by owner directive; publishing needs are handled by mirrors.
- **Git submodules**: poor ergonomics and easy to desynchronize. Rejected.
- **Nx/Turborepo**: pnpm + `just` suffices; Turborepo may be added later for caching only.

## Consequences

- Positive: consistent versions; enforced EE boundary; easy contributor onboarding.
- Negative: a large, polyglot repo, so CI must use path filters, per-toolchain jobs and caching (sccache, pnpm store, Gradle/SPM caches); mirror publishing adds release tooling.
- Risks and mitigations: an accidental EE leak into AGPL crates is caught by a CI dependency-direction check.

## Fallback / revisit trigger

If CI p50 wall time for a typical PR exceeds 20 minutes despite caching, introduce remote build caching. Splitting repos requires a superseding ADR.
